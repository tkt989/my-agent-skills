# 作業とコード変更のカード可視化

作業の順番、コード修正の内容、影響範囲を、すぐ判断できる HTML フラグメントにする。
複数の情報を横に詰め込むより、1 枚ずつ縦に並べる。カードには「何が変わるか・なぜ変えるか・どこに影響するか・確認方法」を必要な範囲で入れ、読み手が次に何をすべきか迷わないようにする。

## 入力を整理する

1. 会話または指定資料から、作業または変更を抜き出す。
2. 作業フローなら実行順に並べ、各作業に短い状態を付ける。例: `要対応`、`一部不足`、`公開前`、`完了`、`運用`。
3. コード修正なら、変更対象を役割ごとにまとめる。例: `UI`、`ロジック`、`設定`、`テスト`、`ドキュメント`。
4. 各コード変更について、ファイルまたはコンポーネント、変更の要点、下流への影響、検証方法を確認する。対象が不明なら推測せず `要確認` と表示する。
5. すでに分かっている事実だけを書く。不明な認証情報、URL、実行結果は推測しない。
6. コマンドが有用なときだけ、短い `code` 要素として載せる。

## 表現を選ぶ

### 作業フロー・リリース計画

- カードを実行順に並べる。
- 番号、作業名、状態、行うことを表示する。
- 公開・運用など、順番が重要な内容に使う。

### コード修正・差分の説明

- カードを `UI`、`ロジック`、`設定`、`テスト` などの役割順に並べる。時系列がある場合だけ番号を付ける。
- カードの見出しは `ファイル名 — 変更の要点` のように具体的にする。
- 説明を次の短いブロックに分ける。
  - `変更`: 何を追加・修正・削除するか。
  - `影響`: 呼び出し元、設定、利用者の操作、互換性への影響。
  - `確認`: 実行するテスト、手動確認、確認すべき画面。
- 依存関係が 3 つ以上あるときは、カードの前に短い矢印図または Mermaid 図を足して、変更元から影響先への流れを示す。
- 変更していない箇所や、未確認の動作を「完了」と見せない。リスクがある場合は、橙または赤紫の状態で明記する。

## HTML の作り方

- 明示的に書き込み可能な作業ディレクトリに、用途が分かる ASCII 小文字・ハイフン区切りの `.html` ファイルを作る。
- 完全な Web ページではなく、`<div>` から始まる HTML フラグメントにする。`<!doctype>`、`html`、`head`、`body` は含めない。
- ルート要素には固有 ID を付け、その ID で CSS の影響範囲を限定する。
- 全体の幅は `width: min(100% - 32px, 680px)` を基本にし、`margin: 22px auto` で中央に置く。画面横幅いっぱいにはしない。
- カードは `grid-template-columns: 1fr` で縦に並べ、十分な間隔を取る。画面が広くても複数列にはしない。
- 各カードを `article` とし、カード内に番号または役割、見出し、状態、説明を置く。
- 手順ごとに青・橙・紫・緑・赤紫など異なるアクセント色を使う。色だけで状態を伝えず、必ず状態テキストも置く。
- アクセント色は左端の細い帯、番号バッジ、状態テキスト、淡い背景に繰り返して使う。派手な全面塗りは避け、本文の読みやすさを保つ。
- 小さい画面では左右余白を狭め、タイトル・状態・コードが折り返せることを確認する。

## 推奨構造

```html
<div id="workflow-cards">
  <style>/* #workflow-cards 配下だけに適用する CSS */</style>
  <h2>計画または変更概要のタイトル</h2>
  <p class="lead">短い補足</p>
  <div class="grid" role="list">
    <article class="release-card s1" role="listitem">
      <div class="card-head">
        <span class="number">1</span><h3>作業名または変更対象</h3><span class="status">要対応</span>
      </div>
      <p>作業内容、または変更・影響・確認方法。</p>
    </article>
  </div>
</div>
```

## 仕上げ

1. HTML を読み返し、リテラルの `\\"` や `\\n` が混じっていないことを確認する。
2. 各状態が本文を読まずに見分けられるか、カードが縦一列か、最大幅が設定されているかを確認する。
3. コード修正の可視化では、変更対象・影響・確認が欠けていないことを確認する。
4. 会話内で表示する場合は、作成した HTML ファイルの可視化コンテンツ参照を返す。ユーザーがローカルで開くよう依頼した場合だけ、ブラウザで開く。
